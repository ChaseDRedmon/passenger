An IDE for C# and .NET, written in C#.

Passenger edits, builds, runs, tests, debugs and profiles C# and modern .NET, with an editor, a debugger and a profiler of its own. It works the way JetBrains Rider does and looks like itself. It knows Avalonia's XAML as well as it knows C#, and your coding agent can use all of it, as you do.

Beside everything an IDE for C# does, three things set Passenger apart.

An IDE your agent can drive

Passenger serves the Model Context Protocol, the standard coding agents use to reach their tools. Through it an agent works in the IDE, not only in your files: it asks the language server instead of guessing from the text, and checks what it changed by building, testing and running it.

It works as you do

It finds where things are declared and used, reads the warnings, renames, fixes and formats code as the IDE does. It builds, runs and tests. It sets breakpoints, steps, reads and changes variables, applies Hot Reload and profiles a run. It searches and replaces across files, commits, resolves conflicts, adds packages, types into the terminal and looks at the window.

It tries the app it builds

When the program is an Avalonia app, or a WPF app on Windows, the agent sees it as a person testing it would: a picture of each window, the tree of its controls with their text and state, and clicks, typing, keys and scrolling sent to the window, which never takes the focus or moves your pointer. It reads the app's binding errors and can break on a property's change.

Your window, or one of its own

With --mcp-attach, the agent joins the Passenger window you have open over the folder it works in. Its breakpoints and stops show in your editor, its runs in your Run window, and the status bar names what it is doing. A window lets agents in only once you turn on Settings › MCP Server › Enable MCP Server, through a socket in your own user's folder, and the first time an agent uses a tool that changes anything, Passenger asks you.

With --mcp and a folder or solution, the agent starts a Passenger of its own with no window, for work it does alone.

The agent starts Passenger from where it is installed:

  • macOS/Applications/Passenger.app/Contents/MacOS/Passenger
  • Windows%LOCALAPPDATA%\PassengerIDE\current\Passenger.exe
  • Linux~/.local/bin/passenger
Claude Code 
claude mcp add passenger -- \
    /Applications/Passenger.app/Contents/MacOS/Passenger \
    --mcp-attach

Or for everyone working in a repository, in its .mcp.json:

{
  "mcpServers": {
    "passenger": {
      "command": "/Applications/Passenger.app/Contents/MacOS/Passenger",
      "args": ["--mcp-attach"]
    }
  }
}
Claude Desktop

In Settings › Developer, choose Edit Config, add Passenger, then restart Claude:

{
  "mcpServers": {
    "passenger": {
      "command": "/Applications/Passenger.app/Contents/MacOS/Passenger",
      "args": ["--mcp-attach"]
    }
  }
}

On Windows the command is Passenger.exe's full path, each \ written \\.

Codex CLI 
codex mcp add passenger -- \
    /Applications/Passenger.app/Contents/MacOS/Passenger \
    --mcp-attach

Or in ~/.codex/config.toml:

[mcp_servers.passenger]
command = "/Applications/Passenger.app/Contents/MacOS/Passenger"
args = ["--mcp-attach"]
Codex desktop app

In Settings › MCP servers, choose Add server, name it passenger, choose STDIO, give Passenger's path as the command and --mcp-attach as its argument, then save and choose Restart. The app and the Codex CLI share their settings, so adding it in one adds it to both.

Any other agent that can add an MCP server connects the same way.

The Avalonia developer's IDE

Passenger is built with Avalonia, and it gives .axaml files the help C# gets, from the project's own assemblies and Avalonia's own compiler and previewer. None of it needs an Avalonia Accelerate licence.

XAML as you type

Completion of controls, properties, attached properties, values, resources, selectors and binding paths checked against x:DataType. The XAML compiler's errors on their lines. Go to Declaration into C#, rename of x:Name, Reformat Code, Extract Resource and Extract Style, and a missing property, command or converter made from where it is used.

XAML Preview draws the file beside it with the project's own Avalonia, following each edit.

The running app, from its XAML

Debug an Avalonia app and the Live Visual Tree shows its controls as they are, each property with where its value came from and each style with why it applies or not. The XAML shows each binding's value after its line.

A binding that fails is a line in the Run or Debug console linked to its XAML, a row in Problems with a fix where there is one, and, if you choose, a stop like an exception's. Breakpoints go on an element, on one of its attributes, or on a property's next change.

Frames in the profiler

Profile an Avalonia app and its frames are charted with what each cost, and their layout listed by control type and then by control, each row opening its XAML. Avalonia's debug overlays are a toggle in the Run and Debug windows.

Failed tests pictured

When an Avalonia.Headless test with xUnit v3 fails, its result carries a picture of each window as it was, popups drawn in.

New projects

New Solution and New Project offer Avalonia's templates, and install them when they are missing.

WPF's XAML too

WPF projects get the same XAML help on every system: completion, checks, navigation, formatting and the refactorings. On Windows, XAML Preview draws WPF files, and the Live Visual Tree and binding errors work while a WPF app is debugged. Elsewhere a WPF project builds for its code help and says it runs only on Windows.

Rider's ways, its own look

If you know Rider, you know where things are in Passenger. It is still its own IDE, written in C#, and it looks like itself.

Your hands already know it

Its keys are Rider's Visual Studio keymap, or on a Mac its Visual Studio OSX keymap, chords included, and Settings › Keymap changes any of them. Its actions have Rider's names: Search Everywhere, Show Context Actions, Extend Selection, Surround With, Complete Current Statement, Run to Cursor.

It behaves as Rider does where that matters: tool windows in IntelliJ's six places, files saved as you go, Local History, a rename across files undone as one step, Rider's file nesting in the Solution view, and Rider's XML formatting for XAML. The toolbar is the window's title bar, as Rider's is, on Windows, macOS and most Linux desktops.

Two looks of its own

Passenger, the default, takes the app icon's blue: a blue-to-teal title bar, the window's areas told apart by shade rather than lines, and an amber mark wherever the window says where you are.

Harbour is warmer and rounder: the icon's teal on linen by day and a warm charcoal by night.

Each comes in dark and light, following your system or your choice, and Rider's colours for the code are a choice under either.

The tour

Everything in Passenger is .NET, from the window to the debugger, over the libraries a C# IDE needs: Roslyn, MSBuild, ICorDebug, EventPipe, VSTest and Microsoft.Testing.Platform.

The editor

A text control of its own over an immutable rope: multiple carets, folding, soft wrap, Extend Selection, live, postfix and surround templates, inlay hints, the symbol at the caret lit through the file, and splits, with tabs in windows of their own. A key costs what it changed, not the file's size: tests hold it in twenty thousand lines and on a line of a million characters.

C# from Roslyn

Colours as you type, then the language server's: diagnostics, completion, hovers, signature help, quick fixes and refactorings such as Change Signature, Extract Interface, Move and Safe Delete, a rename that renames the type's file, Go to Declaration, Implementation and Base Symbols, Find Usages, call and type hierarchies, and decompiled library sources. Problems lists the whole solution's without a build.

A debugger of its own

Over the runtime's ICorDebug: breakpoints with conditions, hit counts and log messages, exception breakpoints, stepping through async code, Smart Step Into, the values methods returned, Run to Cursor and Set Next Statement, threads and frames, variables you can open and set, watches, and the values each line used drawn after it.

Edit the code while debugging and Hot Reload puts it in the program, paused or running. A frame in a library without symbols shows its code, decompiled. Attach to a .NET program already running, on a Mac too with nothing to set up. Data breakpoints on Windows x64.

A profiler too

Sampling over EventPipe, from a program's first instruction or attached to one already running: its call tree, hot spots, flame graph, allocations and garbage collections, narrowed to any stretch of the timeline.

A memory snapshot counts the heap by type and shows what keeps an object alive and how much it holds. Two snapshots compared say which objects are new, which died and which survived.

Git

The Commit window with its changes, the log with its branch graph and branches, side-by-side diffs with the changed words marked, blame, change bars in the gutter that roll a change back, the history of a file, a folder or a selection, stashes, push, pull and fetch, and conflicts resolved in a three-way merge.

Find anything

Search Everywhere, Go to File, Go to Symbol and Find Action. Find and Replace in Files across the solution, a project, a folder or a scope, with a file mask and a preview. Find Usages in a window of its own, Recent Files and Recent Locations, bookmarks and File Structure.

Project files

In a .csproj, .props or .targets: completion of elements, properties, items and their values, and of package ids and versions from your feeds, the version going to Directory.Packages.props under central package management. A property's hover shows its evaluated value and where it was set. Go to Declaration reaches the SDK's own files, and the evaluation's errors sit on their lines.

The web languages

JavaScript, TypeScript, HTML, CSS, SCSS, Less and JSON through their language servers: completion, checks, navigation and formatting, TypeScript on the project's own version and JSON against its schema. ESLint's problems show as you type with its fixes, and the project's own Prettier formats on Reformat Code and on save. Razor and Blazor files get C# and HTML help together.

Build and run

A Solution view of the solution and its projects as MSBuild evaluates them, builds with their errors in Problems, run configurations from your launch profiles, consoles whose stack frames and compiler messages link to their lines, the browser opened for a web project, and Hot Reload under dotnet watch.

Unit tests

xUnit, NUnit, MSTest and TUnit, through VSTest or Microsoft.Testing.Platform: tests found from the code before any build, run marks in the gutter, results grouped and filtered, failures rerun, a run until one fails, and any test debugged.

NuGet

Search the feeds your nuget.config names, then install, update and remove packages for each project, with central package management. A version with a known vulnerability is marked, with the lowest one that fixes it.

Terminal

A terminal emulator of its own with a shell per tab, where vim, less and htop run full-screen. A console program can run and be debugged in it.

Local History

Every version of your files Passenger has seen, for five days of work, whatever Git knows: compared, labelled and put back.

Windows and layout

Tool windows docked or floating, editor tabs split or in windows of their own, a window for each solution, and each solution's layout kept. New Solution starts from any template dotnet new has.

How to install on Linux

Passenger needs:

  • A .NET SDK, version 10 or later. It builds and runs your projects with it, and its language server, project host and debugger run on it.
  • Git, for version control.
  • Node.js, for JavaScript, TypeScript, HTML, CSS and JSON: 22.22.2 or later for TypeScript. C# and XAML do without it.

Every release, with its notes and its SHA256SUMS, is on GitHub.
